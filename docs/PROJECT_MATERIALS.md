# Материалы и проектная графика

Существующие project.json/API/CLI и schemaVersion1 knowledge остаются допустимыми.
Новые поля additive; schemaVersion проекта остаётся2. Старые документальные сцены
без doc.profile используют прежний исторический профиль для совместимости.
Новые пакеты, кроме встроенного id=rurikids, получают generic профиль: без карты
Руси, родословной Москвы и дат862–1598. [0,0] в внутреннем scene.era означает
отсутствующую эпоху generic сцены, а не утверждение о календарном годе.

## Подготовка реальных материалов, офлайн

В GUI «Сценарий и материалы → Подготовить материалы новой темы» введите тему и JSON:

```json
[{"id":"journal","title":"Автор, название, дата, страница","excerpt":"Точная выдержка пользователя, не сгенерированный факт."}]
```

url необязателен, если задан — http(s); он **не скачивается**. Можно использовать
локальные книги/архивы/заметки без выдуманной ссылки. Через POST
`/api/materials/prepare` передаются `{topic,sources}` с JSON Content-Type. Сервер
возвращает `{pack,report,gaps}`. Абзацы становятся кандидатами с точной quote,
source reference, unknown/confidence0/needsReview=true. Не выполняется независимый
фактчекинг, поиск в интернете или автоматическое установление дат/мест/родства.

Кнопка «Передать в таблицу проверки» заполняет existing documentary wizard; проект
не меняется до явного сохранения. «Использовать для нового проекта» переносит
полный пакет в форму создания. Полные knowledge-пакеты schemaVersion1 принимают
GUI create и CLI `new --format documentary --materials package.json`. Старый
production brief формат sources/claims (с date строкой) также остаётся допустим.
Пакеты разных форматов не следует смешивать.

Для generic полного пакета обязательны прежние knowledge поля:
`schemaVersion:1, id, topic, sources, claims`. В claim нужны уникальный id, text,
status (supported/disputed/hypothesis/unknown), date:{value,precision}, place,
confidence0…1, needsReview:boolean, sources:[sourceId]. person/era необязательны.
Неизвестные даты не заменяются угаданными; каждый needsReview виден в QA.

## Графика полного knowledge-пакета

```json
{"graphics":{
  "places":[{"id":"a","label":"Место по материалу","x":0.3,"y":0.4,"claimIds":["claim1"]}],
  "routes":[],
  "genealogy":[]
}}
```

- x/y — нормализованные координаты0…1 условной схемы, **не** широта/долгота.
- routes: `{from:placeId,to:placeId,claimIds:[...]}`. Нет догадок по названиям мест.
- genealogy: `{id,name,parent?:nodeId,dates?:string,claimIds:[...]}`. Родитель должен
  существовать; циклы запрещены. Отсутствующие даты подписываются «дата не указана».
- Каждая запись ссылается минимум на одно существующее утверждение. Это проверка
  ссылки, а не автоматическое доказательство связи. До50 записей на коллекцию.
- Дерево показано фрагментами до4 узлов; связи рисуются только между заданными
  родителями и детьми, присутствующими в текущем фрагменте. QA предупреждает,
  если длительности не хватило показать все узлы. Лучше небольшие тематические пакеты.
- Timeline строит диапазон по era и точным годам. При отсутствии численных дат
  выводит «Точные годы в материалах не указаны», а не862.
- Без places не создаются сцены карты; без genealogy не создаются деревья.

Для визуального утверждения нужны реальные кадры Chrome: после сохранения
`node render.mjs timeline ID`, затем `node render.mjs frames ID --per-scene 3`.
SVG storyboard и DOM-тест **не** подтверждают итоговую картинку.
